# 07 — Data & Database

## 1. Databases and roles

| Database | Contents | Schema source |
|----------|----------|---------------|
| `univarse_platform` | Control plane ([03 §1](03-domain-model.md)) | `packages/db/prisma/platform/schema.prisma` |
| `univarse_pool_NN` | Many tenants, RLS-isolated | `packages/db/prisma/tenant/schema.prisma` |
| `univarse_t_{slug}` | One dedicated tenant (same tenant schema) | same |

### PostgreSQL roles (per database)

| Role | Privileges | Used by |
|------|-----------|---------|
| `univarse_migrator` | Owner of schema objects. Runs DDL | Migration job only (CI/CD), never the running app |
| `univarse_app` | `SELECT/INSERT/UPDATE/DELETE` on tables, `USAGE` on sequences. **`NOBYPASSRLS`, not owner** | API + worker |
| `univarse_app_platform` | CRUD on platform DB only | API/worker platform modules |
| `univarse_readonly` | `SELECT` on a curated set of reporting views. RLS still applies | Reporting, read replica |
| `univarse_audit_writer` (optional) | `INSERT` only on `audit_event` | Audit writer path |

- Revoke `UPDATE, DELETE` on `audit_event`, `ledger_entry`, `course_result`, `score_sheet_event` and `outbox_event` (except `published_at`) from `univarse_app`. Append-only is **enforced by grants**, not by convention.
- `PUBLIC` has no privileges. `REVOKE ALL ON SCHEMA public FROM PUBLIC`.
- The superuser/admin credential is stored in the secret manager, used only for break-glass, and audited.

## 2. Naming & column conventions

- Table names: `snake_case`, **singular** (`course_offering`). Prisma models are PascalCase and mapped with `@@map`.
- Columns: `snake_case` (`@map`). Foreign keys are `<entity>_id`.
- Primary keys: `id uuid DEFAULT uuidv7()` (time-ordered, index-friendly, not guessable in sequence).
- Every tenant table: `tenant_id uuid NOT NULL` as the **first column of every composite index and unique constraint**, plus `UNIQUE (tenant_id, id)`.
- **Every foreign key is composite on `(tenant_id, …)`** and references `(tenant_id, id)`. PostgreSQL validates FKs *without* applying RLS, so a single-column FK would let a row reference another tenant's row by UUID. The RLS checker fails any FK that doesn't include `tenant_id`.
- Standard columns: `created_at timestamptz NOT NULL DEFAULT now()`, `updated_at`, `created_by uuid`, `updated_by uuid`, and `version int NOT NULL DEFAULT 0` for optimistically locked entities.
- Money: `bigint` kobo, with column names ending in `_kobo`. Scores: `numeric(5,2)`. GPA: `numeric(4,2)`. Never `float`/`real`/`double`.
- Enums: PostgreSQL enums via Prisma for stable sets. Lookup tables for tenant-configurable sets (remark codes, fee categories).
- Text search: `pg_trgm` GIN indexes on name/matric fields for fuzzy search.
- Soft delete: **avoid.** Use explicit `status` (`ARCHIVED`, `VOID`, `REVOKED`). Hard delete only for true drafts and via retention jobs.

## 3. Row-Level Security (tenant isolation)

### 3.1 Policy template (applied to every tenant table in a migration)
```sql
-- generated by tools/rls/apply.ts for each tenant table
ALTER TABLE {t} ENABLE ROW LEVEL SECURITY;
ALTER TABLE {t} FORCE ROW LEVEL SECURITY;
CREATE POLICY {t}_tenant_isolation ON {t}
  AS PERMISSIVE FOR ALL TO univarse_app, univarse_readonly
  USING      (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid)
  WITH CHECK (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid);
```

### 3.2 Setting the context (Prisma extension, simplified)
```ts
export function forTenant(base: PrismaClient, tenantId: string) {
  return base.$extends({
    query: {
      $allModels: {
        async $allOperations({ args, query }) {
          const [, result] = await base.$transaction([
            base.$executeRaw`SELECT set_config('app.tenant_id', ${tenantId}, true)`,
            query(args),
          ]);
          return result;
        },
      },
    },
  });
}
```
For interactive transactions, the `TenantTx` helper runs `set_config` as the first statement inside `$transaction(async tx => …)`. **All** tenant data access goes through `TenantPrismaService`, and an ESLint rule bans importing the raw tenant `PrismaClient` elsewhere.

### 3.3 Enforcement in CI (`tools/rls/check.ts`)
After migrations run on the test DB, the checker queries `pg_class` / `pg_policies` and fails the build if any table in the tenant schema (except an explicit allowlist, e.g. `_prisma_migrations`):
- lacks `tenant_id`, or
- has `relrowsecurity = false` or `relforcerowsecurity = false`, or
- lacks the `tenant_isolation` policy, or
- has a unique index/constraint not starting with `tenant_id`, or
- has a foreign key that doesn't include `tenant_id`.

Policies are applied with the SQL helper `univarse_enable_tenant_rls('<table>')` (created in the first tenant migration), which enables and forces RLS and creates the `tenant_isolation` policy.

### 3.4 Isolation tests
The integration suite creates two tenants with identical data shapes and asserts, for every repository, that tenant A's context can never read, update or delete tenant B's rows. It also asserts that no context at all returns zero rows. See [12 §3](12-testing-strategy.md).

## 4. Migrations

- Tool: Prisma Migrate. **Custom SQL** (RLS policies, grants, triggers, partial indexes, `ltree`) goes in the same migration folder's `migration.sql`, appended after Prisma's generated DDL.
- **Expand → migrate → contract.** A release never removes or renames something the previous release still uses:
  1. Release N: add new column/table (nullable or defaulted), write to both, backfill in a job.
  2. Release N+1: read from new, stop writing old.
  3. Release N+2: drop old.
- Destructive statements (`DROP`, `ALTER … TYPE`, `SET NOT NULL` on big tables) are flagged by the CI migration linter (e.g. Squawk) and need a `-- migration-approved: <reason>` annotation.
- Big-table safety: `CREATE INDEX CONCURRENTLY` (in its own migration), add constraints `NOT VALID` then `VALIDATE`, and batch backfills (≤ 5k rows per batch).
- **Migration runner:** a platform job applies migrations shard by shard (platform DB first, then pools, then dedicated DBs), records `MigrationRun` status and stops at the first failure. The deploy pipeline waits for success before rolling out new app pods.
- Every migration is tested against a copy of an anonymised production-sized dataset in staging before the prod release.

## 5. Indexing guidelines

- Index every foreign key: `(tenant_id, fk)`.
- Index common access paths:
  - `student (tenant_id, matric_number) UNIQUE`
  - `course_registration (tenant_id, student_id, semester_id) UNIQUE`
  - `course_result (tenant_id, student_id, semester_id)`
  - `payment_transaction (gateway, gateway_reference) UNIQUE`
  - `invoice (tenant_id, payer_id, session_id)`
  - `audit_event (tenant_id, entity_type, entity_id, occurred_at DESC)`
  - `outbox_event (published_at) WHERE published_at IS NULL`
- Partial unique indexes for "only one active" rules: `academic_session (tenant_id) WHERE status = 'ACTIVE'`, `hostel_allocation (tenant_id, bed_space_id, session_id) WHERE status IN ('HELD','CONFIRMED')`.
- Review `EXPLAIN (ANALYZE, BUFFERS)` for every new list/report query against staging-sized data. p95 query time budget: 50 ms for OLTP paths.

## 6. Integrity rules in the database (defense in depth)

- `CHECK` constraints: scores `BETWEEN 0 AND 100`, `amount_kobo > 0` on payments, `valid_to > valid_from`, `level IN (100..700)`.
- FKs with `ON DELETE RESTRICT` by default. `CASCADE` only for true composition (score entries of a draft sheet).
- Triggers only for: `updated_at`, the audit hash chain, and preventing updates to immutable rows (belt-and-braces on top of grants). **No business logic in triggers.**

## 7. Audit log design

```sql
CREATE TABLE audit_event (
  id uuid PRIMARY KEY DEFAULT uuidv7(),
  tenant_id uuid NOT NULL,
  occurred_at timestamptz NOT NULL DEFAULT now(),
  actor_type text NOT NULL,          -- USER | SYSTEM | PLATFORM_STAFF
  actor_id uuid,
  action text NOT NULL,              -- 'results.scoresheet.approve_hod'
  entity_type text NOT NULL,
  entity_id uuid,
  before jsonb, after jsonb,         -- redacted of secrets
  reason text,
  ip inet, user_agent text, request_id text,
  prev_hash bytea NOT NULL,
  hash bytea NOT NULL                -- sha256(prev_hash || canonical_json(row))
);
```
- The hash chain is per tenant. The previous hash is fetched with an advisory lock per tenant to serialise appends. A daily job verifies the chain and anchors the latest hash to the platform DB (and optionally external WORM storage).
- Partition by month (`occurred_at`) once volume warrants it.

## 8. Encryption of sensitive fields

- **Envelope encryption:** a per-tenant data key (DEK), wrapped by a KMS key (KEK), cached in memory for ≤ 1h. AES-256-GCM with a random 96-bit IV. The stored format is `v1:{keyId}:{iv}:{ciphertext}:{tag}`.
- Encrypted fields: NIN, TOTP secrets, gateway secret keys, webhook secrets, bank details for refunds, medical notes.
- Searchable encrypted fields (e.g. NIN uniqueness) additionally store an HMAC-SHA256 **blind index** with a separate key.
- Key rotation: new DEK version for new writes, with background re-encryption. Old key IDs stay decryptable until re-encryption completes.

## 9. Data lifecycle and retention (summary; authoritative table in [16](16-compliance-ndpa.md))

| Data | Retention |
|------|-----------|
| Academic records (course results, transcripts, graduation) | **Permanent** |
| Financial records (invoices, payments, ledger, receipts) | ≥ 6 years after the session ends `[VERIFY]` |
| Unsuccessful applicant data | 24 months after the cycle closes, then deleted/anonymised |
| Session records, login attempts | 12 months |
| Application logs | 30 days hot, 12 months archived (no PII payloads) |
| Audit events | 10 years minimum for academic/financial actions |
| Offboarded tenant data | Deleted 60 days after offboarding + backup expiry window |

## 10. Backups (summary; detail in [10](10-infrastructure-and-deployment.md))

- Managed Postgres with continuous WAL archiving: **PITR ≥ 14 days** (prod 35 days).
- Nightly encrypted **logical per-tenant exports** (by `tenant_id`), because a pooled DB can't be restored for one tenant from a physical backup. These exports are the tool for single-tenant recovery and offboarding.
- Quarterly **restore drills** (full cluster and single tenant), with timings recorded.

## 11. Seed and test data

- `packages/db/seed/`: deterministic seed with two tenants (`demo-uni`, `test-poly`), realistic Nigerian names, every role, a full academic year, and sample payments in gateway **test** mode.
- **Production data never leaves production.** Staging uses synthetic data or an anonymised copy (names, emails, phones, NIN, DOB shifted; scores kept) produced by a reviewed anonymisation script.
