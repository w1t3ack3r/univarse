## Why

Every tenant query depends on `app.tenant_id`, which RLS reads. Today the app connects to Postgres directly, so a server connection belongs to one client at a time. Under transaction pooling, PgBouncer hands the same server connection to a different client after each transaction. Anything that outlives a transaction on that connection then reaches the next client, and that includes a tenant context set at session level. "Safe by design" is an argument, not a test. This spec makes it a test.

A survey of the code (2026-10-13) found:

- **No session state in production code:**
  - no session-level `SET` or `set_config(…, false)`;
  - no session advisory locks (`pg_advisory_xact_lock` only);
  - no `LISTEN`, `PREPARE`, temporary tables or holdable cursors.
- **What transaction pooling changes, which the design must cover:**
  1. **The UTC session.** Every connection asks for `-c TimeZone=UTC` in its startup `options` (`packages/db/src/pool.ts`). PgBouncer tracks `TimeZone`, including when it is given through `options`, by its documentation. That has to be **proven**, because a dropped option would shift every stored timestamp (found once before, 2026-10-05).
  2. **Saturation shedding (ADR-026), corrected in revision 2:**
     - **Transactions keep their own deadline:** in the pinned Prisma 7.10, `maxWait` covers awaiting the adapter's transaction start, and the adapter awaits `BEGIN` before returning. Behind PgBouncer, `BEGIN` waits in PgBouncer's queue. So a saturated transaction ends in **whichever deadline fires first**: Prisma's 2 s P2028 (already mapped to `server.busy`) or PgBouncer's 2 s `query_wait_timeout`. With equal deadlines, either may win.
     - **The gap is queries outside a transaction,** such as an uncached platform lookup (the tenant resolver, product checks). No `maxWait` applies to them. They wait in PgBouncer's queue until its `query_wait_timeout` ends them, with an error the app doesn't map today, so they would be answered 500.
     - **Why the deadlines are tested apart:** with both at 2 s, a test could pass through the P2028 handler and mask a missing mapping. So PB7 tests the non-transaction path, plus a transaction start where PgBouncer's deadline is made to win.
  3. **Prepared statements.** Prisma's pg adapter names a statement only if a `statementNameGenerator` is configured, and none is. PB6 proves that the app relies on no named statement.

## Decisions

The owner supports D1–D4 and D6 (review of revision 1); D5 is decided as two profiles.

- **D1, where PgBouncer comes from (revision 4): PgBouncer built from verified upstream source, on distroless.**
  - **Source:** PgBouncer **1.26.1** (revision 5; revision 4 pinned 1.26.0), from the upstream tarball, checked against its published SHA-256 (`00886a2994b4844cd37110970df777772cfc42a74c400522c82fba509a3f42d9`). The hash is pinned in the Dockerfile; upstream publishes no signature.
  - **Build:** a pinned Debian 13 builder (`debian:trixie-slim` by digest), configured `--without-cares --without-pam --without-ldap --without-systemd`, building only the `pgbouncer` binary.
    - **DNS goes through libevent** (`adns: evdns2`), so c-ares and its three unfixed HIGH findings aren't present.
  - **Runtime:** `gcr.io/distroless/base-debian13:nonroot`, pinned by digest, the same distroless Debian 13 family as the app images.
    - It provides glibc, OpenSSL (`libssl3t64`), zlib and zstd, **with its own package records**, which the scanners read.
    - Only two things are copied in: the `pgbouncer` binary, and libevent (`libevent-2.1.so.7`) with its package record (PB10).
  - It runs as non-root, with a read-only root filesystem and no capabilities.
  - The same image runs in CI, in compose locally, and later in the local stack (item 7.1).
  - **Rejected, with measurements (2026-10-14):**
    - **Debian slim plus PGDG's `pgbouncer` (the accepted revision 3): 52 HIGH, all unfixed.**
      - 45 are in base packages PgBouncer doesn't need (util-linux, perl, ncurses, systemd).
      - 3 are in `libcares2`.
      - 2 are flagged against PgBouncer itself (below).
    - **PGDG's binary copied onto distroless:** it still needs c-ares.
- **D2, client authentication: an `auth_file` of SCRAM verifiers.** The verifiers are copied exactly from PostgreSQL by `pnpm db:setup`, which already runs as the superuser (PB9).
- **D3, what runs through PgBouncer: all three suites.**
  - **Through PgBouncer:** the DB isolation suite (including the timezone and pool tests), the crypto integration suite, and the API integration suite.
  - **Direct:** migrations, `db:setup`, seeding and `rls:check`. Prisma Migrate takes a session advisory lock.
- **D4, the CI shape: a separate job, plus a comparison job that joins it** (revision 2: PB3).
- **D5, pool sizes: two profiles** (owner decision, revision 2), documented side by side under Design:
  - **The probe profile,** `default_pool_size = 2`: the dedicated pooling probes (PB1, PB2, PB5, PB6, PB7), where tiny pools make sharing and saturation certain.
  - **The suite profile,** `default_pool_size = 10`: the unchanged integration suites (PB3). That matches each client's pool of 10 (ADR-026), so `pool.int.spec.ts`, which holds ten transactions open on purpose before checking exhaustion, runs unchanged.
- **D6, where UTC comes from: the client's startup option, plus a role-level default.**
  - The option is the setting.
  - `ALTER ROLE … SET timezone = 'UTC'` on the app roles is a **default** for sessions that send none. It doesn't force UTC over a client's own setting.
  - PB5 proves each half independently.

## Design

**The two profiles (D5).** The same image and auth file serve both; only the pool size differs.

| Setting                     | Probe profile (PB1, PB2, PB5, PB6, PB7)                            | Suite profile (PB3)            |
| --------------------------- | ------------------------------------------------------------------ | ------------------------------ |
| `pool_mode`                 | `transaction`                                                      | `transaction`                  |
| `default_pool_size`         | **2**                                                              | **10**                         |
| `max_client_conn`           | 200                                                                | 200                            |
| `max_prepared_statements`   | 0                                                                  | 0                              |
| `query_wait_timeout`        | 2 s                                                                | 2 s                            |
| `server_round_robin`        | 0 (the default: the most recently used connection is reused first) | 0                              |
| `auth_type`                 | `scram-sha-256`                                                    | `scram-sha-256`                |
| `listen_addr`               | `0.0.0.0` inside the container                                     | `0.0.0.0` inside the container |
| `ignore_startup_parameters` | **unset**                                                          | **unset**                      |
| `max_packet_size`           | the default (2147483647)                                           | the default                    |

**The network mode: a bridge container,** chosen explicitly:

- **Inside the container,** PgBouncer listens on `0.0.0.0:6432`, so it can be reached from outside it.
- **Exposure:** the port is published **only on loopback** (`-p 127.0.0.1:6432:6432`). Nothing on the host's other interfaces reaches it.
- **Reaching Postgres:** PgBouncer connects through `host.docker.internal`, mapped **explicitly to the active Docker daemon's host-gateway IPv4 address** (owner decision A, 2026-10-14): `--add-host=host.docker.internal:<IPv4>`, never `:host-gateway` itself, which can expand to both address families. In CI that is the Postgres service on the runner. Locally it is the native Postgres on the owner's machine.
  - **Discovery** (`tools/pgbouncer/gateway.mjs`): a container of the pinned distroless Node reader image, with a probe host mapped to `host-gateway`, reports its `/etc/hosts`. Exactly one usable IPv4 address for the probe name is required. IPv6 addresses are reported and never used.
  - **Failure is clear and bounded:** a 60 s limit; no IPv4 address, two different ones, or an unusable one (loopback, unspecified, multicast, malformed) each fail with the reason, never a guess or a fallback.
- **Locally, `pg_hba.conf`:** if the native Postgres refuses connections from Docker's address range, a `pg_hba.conf` entry for that range (scram, the app databases only) is needed. That is **the owner's step** on their own Postgres install, never done by a script.
- **Host networking was not chosen:** it would let PgBouncer bind loopback directly, but it isn't uniformly available on Docker Desktop for Windows.

**The jobs and the join (D4, PB3):**

- **`build-test` (existing)** writes machine-readable results for the three suites (vitest's JSON reporter). It uploads them as an artifact, alongside its usual output.
- **`pgbouncer-isolation` (new)** does, in order:
  1. sets up and migrates directly;
  2. starts PgBouncer in the probe profile and runs the probe file (PB1, PB2, PB5, PB6, PB7, PB9);
  3. restarts PgBouncer in the suite profile and runs the three suites through it, writing the same JSON results;
  4. uploads them.
- **`pgbouncer-compare` (new)** has `needs: [build-test, pgbouncer-isolation]`, so it runs only after both have finished. It downloads both artifacts and compares file names, test names, statuses and skips. Nothing depends on fetching an unfinished job's logs.
- **Before merging the implementation:** `pgbouncer-isolation` and `pgbouncer-compare` become **required status checks** on `main`, once the implementation PR has created them and before it merges. The owner instructed this on accepting this spec. The setting change is confirmed with the owner at that point.

**Locally:**

- `pnpm dev:pgbouncer` starts the same image in compose, in either profile.
- `pnpm test:int:pgbouncer` runs the probes and the suites through it, serialized with other integration runs as usual.

**Code changes (small):**

- `isConnectionUnavailable` gains a narrow match for the captured PgBouncer error (PB7);
- `db:setup` writes the auth file, its permissions and `pgbouncer.ini`, and sets the role `timezone` defaults (D2, D6, PB9);
- the PB4 check;
- the probe file;
- the JSON results and the comparison step.

Nothing in `forTenant`, `withTenantTx` or the RLS policies changes.

**What stays open, stated plainly:**

- **The production path:** this proves the app is correct through transaction pooling. Running PgBouncer in the local production-like stack, with TLS, per-role pools (ADR-020 bulkheads) and sizing, is item 7.1.
- **What PB4 can't see:** stored functions, a value cast to a false type, and code outside the scanned TypeScript. The runtime probes cover only what they exercise.
- **The suite profile:** it reuses server connections less aggressively than the probe profile. That's by design: it runs the existing suites unchanged, while the probe profile is where sharing is forced.
- **The relay role (spec 0016)** gets its own pool when that spec is implemented.

## Implementation finding: PB7's captured error, and the host gateway (2026-10-14)

**The capture (PB7, "capture first").** It used a disposable PostgreSQL 18, the platform migrations, and the PgBouncer 1.26.1 image in the probe profile: two server connections, and `query_wait_timeout` of 2 s. Two raw clients held both server connections in open transactions. Both paths then failed with the **same** wrapped error:

| Path                                                                  | Failed after | Error                                                                                                                                                                                                                                                                                                                                        |
| --------------------------------------------------------------------- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| An uncached `tenant.findUnique` outside a transaction                 | 2 531 ms     | `PrismaClientKnownRequestError`, code **`P2039`**, message ``Database error. Code: `08P01`. Message: `query_wait_timeout` ``; `meta.driverAdapterError` is a `DriverAdapterError` "query_wait_timeout" whose `cause` is `{kind: 'postgres', code: '08P01', originalCode: '08P01', originalMessage: 'query_wait_timeout', severity: 'FATAL'}` |
| A `$transaction` start with `maxWait` 5 s (PgBouncer's deadline wins) | 2 395 ms     | The same, without `modelName`                                                                                                                                                                                                                                                                                                                |

- **Recovery:** after the holders were released, the same lookup answered in 42 ms.
- **No uncaught error:** Prisma's adapter pool raised no unhandled error event. The only unhandled one came from the capture's own raw clients before they had listeners.
- **The matcher:** `isConnectionUnavailable` matches this **narrowly**: Prisma's runtime error class itself, code P2039, a `DriverAdapterError` with exactly that message, and a cause with exactly those five fields. PgBouncer reports many of its own errors as `08P01`, so the code alone isn't enough.
- **Its tests:** each field is pinned by a unit test built with Prisma's real class. Each of ten weakenings fails it.
- **Still to come:** the API-level halves (503 with `Retry-After`, recovery, an unrelated error still 500, both mutations) are in the probe file.

**The host gateway (decided: A).** Revision 5's Design mapped `host.docker.internal` with `--add-host=host.docker.internal:host-gateway`. What follows was **observed on this machine's Docker Desktop configuration**; Docker documents that `host-gateway` can expand to both families when IPv6 is configured, so it isn't universal across installations.

- **What this Docker Desktop wrote:** `/etc/hosts` got **both** the IPv4 gateway (`192.168.65.254`) and an IPv6 one (`fdc4:…::254`), which isn't routable from the container.
- **What PgBouncer does with that:** it tries a host's addresses in turn. The first server connection went over IPv4. The next one failed on IPv6 ("Network is unreachable"), and the waiting clients ran into `query_wait_timeout`. A dedicated host name doesn't help, because `host-gateway` writes both families for any name.
- **What worked:** with the IPv4 address itself as the server host, everything worked.
- **CI:** GitHub's Linux runners keep Docker's IPv6 off by default, so `host-gateway` there should resolve to IPv4 only. The `pgbouncer-isolation` job will show it.
- **Decided (owner, 2026-10-14): A.** The daemon's actual host-gateway IPv4 address is discovered at startup, validated, and mapped explicitly (Design). On this machine discovery returns `192.168.65.254`.

## Owner review of the image implementation (2026-10-14)

Implementing PB10 surfaced a policy question and two gaps, now written into PB10.

- **Scanner routing:**
  - **The finding:** on the same image, Grype rates three CVEs in the distroless base HIGH (NVD's rating) that Trivy rates MEDIUM (Debian's): CVE-2026-5435 and CVE-2026-19499 in `libc6`, and CVE-2026-85091 in `zlib1g`.

- **The inventory gaps,** found in the owner's review of `2f64550`:
  - **What was wrong:** the base's files weren't hashed or validated, and missing hashes were silently filtered out.

The base's own record-versus-file deviations are written explicitly, and are allowed only as the pinned base has them.
  - **Immutable references:** inspection, export and the version probe use the resolved image ID.
  - **Tests:** 11 unit tests cover these, with five mutation checks, each failing its intended test.
- **Links and completeness,** found in the owner's review of `38ef2fa`:
  - **What was wrong:** link targets were discarded, so an unowned symlink passed and differently targeted links looked identical. Base files no record lists were left out of the inventory, and a file missing only its SHA-256 passed.
  - **Now:** the tar reader keeps link targets (header, pax `linkpath`, GNU long links) and exact entry kinds. Base links and entry kinds are compared against the pinned base, and only libevent's soname link may be added. Unsupported kinds are rejected. Every regular file is inventoried with a valid SHA-256, and the two kinds of deviation are marked distinctly.
  - **On the real image:** 1 284 file hashes, 340 symlinks with targets, 166 approved absences, and 1 file differing from its record (distroless's `os-release`).
  - **Tests:** 19 inventory tests and 3 tar tests; 11 mutation checks each fail their intended test.
- **The PAX decoder,** found in the owner's review of `ff86783`:
  - **What was wrong:** the reader found `path` and `linkpath` with newline regexes. A link target containing a newline was cut short, so a retargeted base link passed. Text inside a value could pose as a record, disguising an unowned link as a base one.
  - **Now:** pax records are decoded by their declared **byte** lengths, with every boundary and terminator validated. Text inside a value is never read as metadata. Refused explicitly:
    - malformed input: overrunning or zero-padded lengths, a missing newline or key, repeated keys, invalid UTF-8;
    - unsupported input: a size override, or a global header setting a path, link, size or owner.
  - **Owners:** pax `uid`/`gid` overrides are applied.
  - **Failing closed:** a reader error fails the export, inspection or canary, never half-reading the archive.
  - **Tests:** 8 tar tests and 21 inventory tests, including both attacks end to end through `checkFacts`, a UTF-8 byte-length control, and truncated or malformed records.
  - **Mutant:** with the old regex decoder put back, 7 of them fail.
  - **Independent cross-check:** Python's `tarfile` wrote the owner's two archives and a UTF-8 one, and our reader agrees with it exactly on all three.
- **The shared reader's integration,** found in the owner's review of `e156fa1`:
  - **What was wrong:** a truncated stream still succeeded, because the parser had no end-of-stream check. `readFromTar` let decoder errors escape uncaught, terminating Node instead of rejecting to `savedConfig` and `sameImage`.
  - **Now, at end of stream:** the parser has a `finish()`. It refuses:
    - a stream that ends inside a header or inside an entry's data;
    - extended metadata with no entry after it;
    - a missing end-of-archive marker;
    - any data after that marker.

    A parser that has failed stays failed.

  - **One path for every reader:** `consumeTar()` (and `consumeDockerExport()` for `docker export`) feeds the stream, stops it on any error, requires `finish()`, and only then resolves, so errors always reject to the caller. `readFromTar`, `inspect.mjs`, the canary and the PgBouncer inventory all use it.
  - **Cleanup:** `sameImage` removes its temporary tar in a `finally`, so the normal cleanup runs on failure too.
  - **Tests:** 13 tar tests cover genuinely truncated streams, with no padding or end blocks appended: the owner's manifest-then-short-pax case, a partial header, orphan metadata and a missing end marker. Malformed input and premature end are each shown to reject through `readFromTar`, `savedConfig`, `sameImage` and the docker-export reader, which also stops docker. Seven mutation checks each fail their intended test.
  - **Checks still passing:** every image-tool suite. The inspector reads the real PgBouncer image through the new path and passes.

## Owner review of revision 2

The owner found the seven revisions sound, and asked for two proof details.

1. **PB5 runs each UTC control on fresh sessions:**
   - **Why:** `ALTER ROLE … SET` affects only new sessions, so the probe recycles the role's server connections and opens fresh frontend clients after every change.
   - **A baseline first:** the propagation control confirms that a client without the option sees `Africa/Lagos`, before proving the UTC option overrides it.
   - **A third mutation:** skipping the recycle must fail.
2. **PB7 no longer promises that P2028 wins:**
   - **Why:** with both deadlines at 2 s, either path may win.
   - **A new case:** a queued `BEGIN`, with a test-only `maxWait` of 5 s against PgBouncer's 2 s. It captures that wrapped error and requires the same narrow match, 503 and `Retry-After`.
   - **What stays:** the uncached platform lookup and the existing P2028 test.

## Owner review of revision 1

The owner supported D1–D4 and D6, decided D5 as two profiles, and asked for seven corrections, each now in the criteria and design.

1. **Two profiles:** `pool.int.spec.ts` deliberately holds ten transactions open, which a two-connection pool can't serve. The tiny pool now runs only the dedicated probes, and the unchanged suites run with ten (D5, PB3, the profile table).
2. **PB7's diagnosis is corrected:** Prisma 7.10's `maxWait` covers the adapter's `BEGIN`, so a 2 s/2 s race could mask a missing mapping. The test now uses an uncached platform lookup outside any transaction, captures the real wrapped error and matches it narrowly, and checks recovery and an unrelated 500. (Revision 3 adds the queued transaction start.)
3. **Stronger PB1 and PB2:** sharing is shown while all frontend connections stay open. Each tenant iteration checks ids and distinct fixture values as well as counts, and fixtures have equal counts, so a swap fails.
4. **Independent controls:**
   - **PB5:** propagation is proven with a non-UTC role default, and the role fallback with no client option. A role setting is described as a default, not a force.
   - **PB6:** the mutant reuses a stable statement name after a forced backend change, with a control against direct PostgreSQL.
5. **PB4 is tightened:**
   - **More forms:** `RESET`, the shared and unlock advisory-lock variants, `CREATE TEMPORARY` and `SELECT … INTO TEMP`.
   - **Unknown locality refused:** a `set_config` whose locality can't be established.
   - **Limits stated.**
6. **A join point:** both jobs publish machine-readable results, and a comparison job waits for both. Making the new checks required is the owner's repository setting.
7. **PB9 at run time:**
   - **Authentication:** exact SCRAM verifiers, the same username, no forced `user=`.
   - **Tests:** authentication and rotation.
   - **File protection:** Windows ACLs as well as Linux permissions.
   - **Networking:** an explicit bridge mode with a loopback-only published port.
