# Spec 0016: Platform invalidation outbox — database triggers capture every change to the cached platform tables

**Status:** **Draft for review, revision 2 (2026-10-13).** Design only; nothing is implemented. Revision 2 answers the owner's review of revision 1 ([below](#owner-review-of-revision-1)). The owner supports the direction of D1–D5; D3's timing and D6 are revised here. It needs the owner's acceptance and that of [ADR-031](../19-decision-log.md) (proposed with this spec).
**Phase:** 0. A follow-up to [spec 0015](0015-cache-isolation.md), which is complete for today's caches. It does not reopen spec 0015 and is not a Phase 0 exit criterion by itself; it closes the limits spec 0015 recorded.
**Builds on:**

- [spec 0015](0015-cache-isolation.md): the `InvalidationBus`, its channels, the products subscriber and the generation guard (CI3);
- [spec 0002](0002-audit-and-outbox.md) Part B: the tenant transactional outbox and its relay, whose claim pattern this adapts;
- [07](../07-data-and-database.md): migrations, grants and the current rule on triggers;
- [ADR-015](../19-decision-log.md): PgBouncer in transaction pooling (next on the roadmap).

## Why

Spec 0015 makes the API publish an invalidation after it commits a change to `tenant`, `tenant_domain` or `tenant_product`. A static guard (CI10) checks that every writer in the API's TypeScript does so. The owner accepted the guard, and its record keeps three limits open:

- **A type that lies:** a SQL fragment cast through `as unknown as string` reaches a raw template unseen.
- **Behaviour inside the database:** stored functions, and SQL assembled at run time (`EXECUTE 'UPDATE ' || 'tenant'`, `format()`).
- **Writers outside the API's TypeScript:** the seed, a migration, an operator's `psql`, a future service.

Each of these changes a row without a publish, so other instances serve the old value until their cache entry expires (30 s today for products and the tenant resolver).

**The fix is to capture the change where it happens.** A trigger on each of the three tables writes an invalidation event in the **same transaction** as the change. A relay in the worker, on its own least-privileged database role, publishes committed events to the bus. Any writer is covered, whatever its language. A rolled-back change leaves no event, and an event is visible only after its change commits, so publishing after commit holds by construction.

**Where the tables live.** All three are in the **platform** database, outside tenant RLS. The tenant outbox relay ([spec 0002](0002-audit-and-outbox.md) B3–B10) claims per tenant, per shard, under that tenant's RLS context, so it can't be reused as it is. This spec adds a platform relay that keeps its claim pattern (`FOR UPDATE SKIP LOCKED`, outcome recorded in the claiming transaction).

## Decisions

The owner supports D1–D5's direction (review of revision 1). D3's timing and D6 are revised as the owner asked.

- **D1, TRUNCATE: refused.** A row trigger doesn't fire on `TRUNCATE`, and a statement trigger can't name the tenants. A `BEFORE TRUNCATE` trigger on each table **raises**, for every role. Nothing truncates these tables today (checked: no code, test or tool). The event table is protected the same way.
- **D2, the in-code publishes: kept** as the fast path. `ProductService.invalidate()` already publishes directly after commit. The trigger outbox is the guarantee. A change then reaches subscribers twice, which is harmless (an extra eviction).
- **D3, the CI10 static guard: retired only after the complete replacement has passed CI and merged.** That happens in a later, separate PR. CI9 (the one path to full-tenant destruction) stays, because the trigger doesn't replace it.
- **D4, how the relay wakes: polling.** It polls every 250 ms against a partial index, which works through PgBouncer's transaction pooling. `LISTEN`/`NOTIFY` would need a connection that bypasses PgBouncer, with polling still needed as the fallback.
- **D5, the resolver's negative entries: cleared on any tenants message.** The tenant resolver caches by host, and caches **unknown** hosts too (flood protection). A `{tenantId}` message can't name those entries. So on any `uv:tenants:invalidate` message, it evicts that tenant's entries **and every negative entry**. Only platform writes trigger these messages. Its stale-load guard is a **global** generation, which works before any tenant id is known (IO13).
- **D6, undelivered events (revised): expiry counts from after commit, against a shared, enforced maximum TTL.**
  - **The cap:** a shared constant `MAX_TENANT_CACHE_TTL_MS` (proposed **60 s**, in `packages/contracts`) caps every instance's cache TTL. An instance configured above it **refuses to start**.
  - **The clock starts after commit:** each event gets a durable **first-observed** time, stamped by the database with `clock_timestamp()` when a relay first sees it. A relay can only see the event after commit, so this is never earlier than the commit.
  - **The database enforces the wait:** it refuses to mark an event `EXPIRED` until `first_observed_at + MAX_TENANT_CACHE_TTL_MS + 5 s` has passed. By then, every cache entry that could hold the pre-change value has expired (IO12). Until then, the event is retried with backoff.

## Design

**The shared maximum.** `MAX_TENANT_CACHE_TTL_MS = 60_000` lives in `packages/contracts`, so the API and the worker both import it.

- **Startup check:** the config schema gives `TENANT_CACHE_TTL_MS` `.max(MAX_TENANT_CACHE_TTL_MS)`, so an instance configured above it fails validation and refuses to start.
- **In the database:** the migration defines the same value, as an immutable SQL function `public.cache_invalidation_max_ttl()`. A unit test reads the migration and checks the two are equal.

**The event table** (platform database, expand-only migration):

```sql
CREATE TABLE public.cache_invalidation_event (
  id                 uuid PRIMARY KEY DEFAULT uuidv7(),
  channel            text NOT NULL CHECK (channel IN ('uv:tenants:invalidate', 'uv:products:invalidate')),
  tenant_id          uuid NOT NULL,        -- no FK: the tenant may have just been deleted
  source             text NOT NULL,        -- e.g. 'tenant_product:UPDATE'; never row values
  created_at         timestamptz NOT NULL DEFAULT clock_timestamp(),  -- diagnostics only; never used for expiry
  first_observed_at  timestamptz,          -- stamped by the guard trigger: clock_timestamp() at first claim
  attempts           integer NOT NULL DEFAULT 0,
  next_attempt_at    timestamptz NOT NULL DEFAULT '-infinity',
  status             text NOT NULL DEFAULT 'PENDING' CHECK (status IN ('PENDING', 'PUBLISHED', 'EXPIRED')),
  settled_at         timestamptz,          -- stamped by the guard trigger on settlement
  last_error         text                  -- an error class only, as in spec 0002 B9
);
CREATE INDEX cache_invalidation_event_due ON public.cache_invalidation_event (next_attempt_at, id) WHERE status = 'PENDING';
CREATE INDEX cache_invalidation_event_settled ON public.cache_invalidation_event (settled_at) WHERE status <> 'PENDING';
```

**The capture function**, `public.capture_cache_invalidation()`, one for all three tables, with the channel as its trigger argument:

- **Triggers:** two per table. One is `AFTER INSERT OR UPDATE OR DELETE … FOR EACH ROW`, with no `WHEN` clause; the other is the TRUNCATE refusal. Both are `ENABLE ALWAYS`.
- **The `UPDATE` branch:**
  - It returns at once when `NEW IS NOT DISTINCT FROM OLD`, so a no-op update emits nothing. This check lives in the function because a combined trigger's `WHEN` can't reference `OLD` on `INSERT` or `NEW` on `DELETE`.
  - Otherwise it emits the old tenant id, plus the new one when it differs (IO4).
- **The other branches:** `INSERT` emits the new row's tenant id, and `DELETE` the old row's. The tenant id is `id` on `tenant`, and `tenant_id` on the other two tables.
- **Function settings:**
  - `SECURITY DEFINER`, owned by `univarse_migrator`;
  - `SET search_path = pg_catalog, pg_temp`, with `pg_temp` explicitly last;
  - every reference schema-qualified (`public.cache_invalidation_event`);
  - `REVOKE EXECUTE … FROM PUBLIC`. PostgreSQL checks `EXECUTE` when a trigger is created, not when it fires, so capture is unaffected.
- **Default function privileges:** `ALTER DEFAULT PRIVILEGES FOR ROLE univarse_migrator REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC`, so a future function doesn't silently gain `PUBLIC EXECUTE`.
- **No temporary tables:** the app and relay roles keep **no** `TEMPORARY` on the platform database. Each database is created `REVOKE ALL … FROM PUBLIC`, with only `CONNECT` granted.
- **What this is not:** business logic. The function records _that_ a row changed and which tenant it belongs to, nothing about what changed. ADR-031 amends docs/07's trigger rule to allow exactly this.

**The event table's own guards** (`ENABLE ALWAYS`, `SET search_path = pg_catalog, pg_temp`):

- **`BEFORE UPDATE`:**
  - It refuses any change to a settled row, and any change to `id`, `channel`, `tenant_id`, `source` or `created_at`.
  - It allows status only `PENDING` → `PUBLISHED`/`EXPIRED`, and stamps `settled_at := clock_timestamp()` on settlement.
  - It sets `first_observed_at := clock_timestamp()` the first time a claimed row is updated, ignoring any supplied value, and never changes it afterwards.
  - It refuses `EXPIRED` unless `first_observed_at IS NOT NULL AND clock_timestamp() >= first_observed_at + cache_invalidation_max_ttl() + interval '5 seconds'`.
- **`BEFORE DELETE`:** it refuses unless the row is settled and `settled_at < clock_timestamp() - interval '24 hours'`.
- **`BEFORE TRUNCATE`:** it raises.

**Roles and grants (IO17):**

- **The platform app role (`univarse_app_platform`):** `REVOKE ALL ON public.cache_invalidation_event`, which overrides the default privileges that would otherwise give it full DML.
- **The relay role (`univarse_relay_platform`), new:**
  - `LOGIN`, `NOSUPERUSER NOCREATEROLE NOBYPASSRLS`, `CONNECT` only, no `TEMPORARY`;
  - `GRANT SELECT, UPDATE (attempts, next_attempt_at, status, last_error)` on the event table;
  - `EXECUTE` on `public.purge_settled_invalidation_events(limit)`;
  - `ALTER ROLE … SET statement_timeout = '5s'` and `SET idle_in_transaction_session_timeout = '5s'`;
  - its URL (`PLATFORM_RELAY_URL`) is generated by `setup-local` and CI's role step, and given **only to the worker**;
  - behind PgBouncer, it is its own pool.
- **The purge function:** `SECURITY DEFINER` with the same safeguards. It deletes at most `limit` rows, each settled for more than 24 h. The `BEFORE DELETE` guard enforces the same rule underneath it.

**The relay, `PlatformInvalidationRelay`,** runs in the worker, on the relay role's connection:

1. **Claim:** in one transaction with a **3 s** timeout, select up to 200 `PENDING` events with `next_attempt_at <= now()`, `ORDER BY next_attempt_at, id`, `FOR UPDATE SKIP LOCKED`. Then touch them once, so the guard stamps any missing `first_observed_at` (IO7, IO10, IO12).
2. **Expire (D6):** mark `EXPIRED` the claimed events whose `first_observed_at + max + 5 s` has passed. The guard trigger checks the bound, so a wrong relay can't expire early. They are counted in a warning.
3. **Coalesce:** publish each distinct `(channel, tenant_id)` once, oldest first (IO18).
4. **Publish** through `InvalidationBus.publish`, until the **2 s batch deadline**, with each publish's timeout set to `min(5 s, time left)` (IO11).
   - On success, that pair's events become `PUBLISHED`.
   - On the first failure (Valkey unavailable), stop. The remaining events get `attempts + 1`, a backoff and their error class.
   - At the deadline, stop. The remaining events stay `PENDING`, unchanged.
5. **Commit.** A crash before this point leaves every claimed event `PENDING`: before a publish, IO8; after one, IO9.
6. **Housekeeping:** at most once a minute, call the purge function (IO18).

The loop polls every 250 ms when idle (D4) and immediately after a pass that stopped at its deadline or claimed a full batch. Passes never overlap.

**Consumers:**

- **Products:** unchanged. `ProductService` already subscribes in the API and the worker, with its generation guard. Its entry lifetime already counts from the start of the load; IO12 makes that a tested requirement.
- **The tenant resolver** (API) gains a subscriber on `uv:tenants:invalidate`, which today has none:
  - It evicts the tenant's entries and every negative entry (D5).
  - It gains the **global** generation guard (IO13).
  - Its whole-cache `invalidate()` stays, and bumps the generation.

**Ordering and timing:**

- **Publish follows commit by construction:** the relay can only see an event once its change has committed. An eviction can therefore never arrive before the change it announces.
- **The order between events doesn't matter,** because every message means the same thing: evict this tenant.
- **The 2 s target and its conditions** are in IO11. The shared maximum TTL bounds staleness in every case (IO12).

**What stays open, stated plainly:**

- **The owner role can still bypass capture.** `univarse_migrator`, or a superuser, can disable or drop the triggers and functions. Nothing at the database level stops the owner role. The IO15 gate detects it the next time it runs; it does not prevent it.
- **A subscriber that is down when a message is sent** still relies on the cache TTL, now capped by the shared maximum. Pub/sub doesn't queue for absent subscribers.
- **Wall-clock jumps on an instance** can stretch a cache entry's lifetime, because entry expiry uses `Date.now()`. The 5 s expiry margin covers small skew, not a clock stepped backwards by minutes. Moving cache deadlines to a monotonic clock is a small follow-up if the owner wants it.
- **The keyring's forget** (`uv:keys:forget`) stays on its in-code path. Key destruction already publishes after commit with an honest report (spec 0015 CI5–CI9), and `tenant_data_key` is not in scope here.

## Owner review of revision 1

The owner found the architecture right. Five corrections and one explicit test were requested; each is now in the criteria and design.

1. **Expiry must start after commit.**
   - **The problem:** revision 1 measured from `created_at DEFAULT now()`, the start of the writing transaction. A long transaction could commit after the TTL had passed, while another instance had freshly cached the old value, and the relay would then discard the event at once. The relay's own `TENANT_CACHE_TTL_MS` also can't speak for other instances, and had no upper bound.
   - **Now:**
     - `first_observed_at` is stamped by the database with `clock_timestamp()` at first claim, which is always after commit;
     - a shared `MAX_TENANT_CACHE_TTL_MS` is enforced at startup and known to the database;
     - the database itself refuses early expiry;
     - cache lifetimes count from the start of the load;
     - tests cover the long transaction and differing instance TTLs (D6, IO12).
   - **Also:** `now()` in a relay transaction is that transaction's start time, which can come before a commit the relay then sees, so the stamp uses `clock_timestamp()`.
2. **Ordinary writers mustn't erase or settle events.**
   - **The problem:** revision 1 left the API's platform role able to delete events, or mark them `PUBLISHED`/`EXPIRED`.
   - **Now:** the app role has no privilege on the event table. The relay has its own role, with no `DELETE`. Guard triggers enforce, for every role, the status transitions, immutable settled rows, database-stamped times, the expiry bound and deletion only after 24 h settled. Housekeeping goes through a purge function that deletes only old settled events (IO17).
3. **The `SECURITY DEFINER` safeguards are completed:**
   - schema-qualified references;
   - `search_path = pg_catalog, pg_temp`, with `pg_temp` last;
   - `PUBLIC EXECUTE` revoked on the functions and in the migrator's default privileges;
   - no `TEMPORARY` for the app and relay roles, preserved and gated;
   - a shadowing test (IO15, IO16).
4. **The trigger and `WHEN` mismatch is resolved:** the no-op filter moves into the function's `UPDATE` branch, keeping two triggers per table, and the mutation now reads "no no-op check in the `UPDATE` branch" (IO4, IO19).
5. **The whole relay pass is bounded:**
   - a 2 s batch deadline;
   - publish budgets of `min(5 s, time left)`;
   - a 3 s transaction timeout;
   - server-side `statement_timeout` and `idle_in_transaction_session_timeout` on the relay role;
   - a test with 50 distinct tenants and slow, successful publishes;
   - the conditions for the 2 s target, and the backlog behaviour, stated (IO11).
6. **The in-flight negative lookup test is explicit,** and the resolver's generation is global, so it works before any tenant id is known (IO13).

D3 now says the CI10 guard is retired only after the complete replacement has passed CI and merged.
