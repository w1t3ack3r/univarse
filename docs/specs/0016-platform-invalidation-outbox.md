# Spec 0016: Platform invalidation outbox — database triggers capture every change to the cached platform tables

**Status:** **Accepted (2026-10-13)** by the owner: revision 5, after review of `8bad3aa`, with [ADR-031](../19-decision-log.md) Accepted alongside. **Implemented** in two PRs: PR A (the database capture, the relay and its credentials; #73) and PR B (monotonic cache deadlines, the resolver's subscriber); see [Implementation notes (PR A)](#implementation-notes-pr-a) and [(PR B)](#implementation-notes-pr-b). CI10's bindings are retired later (D3). Revisions 2–5 each answered the owner's review of the previous one ([reviews below](#owner-review-of-revision-4)). The owner decided D1–D6 as written, and the 60 s maximum with the existing 30 s default.
**Phase:** 0. A follow-up to [spec 0015](0015-cache-isolation.md), which is complete for today's caches. It does not reopen spec 0015 and is not a Phase 0 exit criterion by itself; it closes the limits spec 0015 recorded.
**Builds on:**

- [spec 0002](0002-audit-and-outbox.md) Part B: the tenant transactional outbox and its relay, whose claim pattern this adapts;

## Why

Spec 0015 makes the API publish an invalidation after it commits a change to `tenant`, `tenant_domain` or `tenant_product`. A static guard (CI10) checks that every writer in the API's TypeScript does so. The owner accepted the guard, and its record keeps three limits open:

- **A type that lies:** a SQL fragment cast through `as unknown as string` reaches a raw template unseen.
- **Behaviour inside the database:** stored functions, and SQL assembled at run time (`EXECUTE 'UPDATE ' || 'tenant'`, `format()`).
- **Writers outside the API's TypeScript:** the seed, a migration, an operator's `psql`, a future service.

Each of these changes a row without a publish, so other instances serve the old value until their cache entry expires (30 s today for products and the tenant resolver).

**The fix is to capture the change where it happens.** A trigger on each of the three tables writes an invalidation event in the **same transaction** as the change. A relay in the worker, on its own least-privileged database role, publishes committed events to the bus. Any writer is covered, whatever its language. A rolled-back change leaves no event, and an event is visible only after its change commits, so publishing after commit holds by construction.

**Where the tables live.** All three are in the **platform** database, outside tenant RLS. The tenant outbox relay ([spec 0002](0002-audit-and-outbox.md) B3–B10) claims per tenant, per shard, under that tenant's RLS context, so it can't be reused as it is. This spec adds a platform relay that keeps its claim pattern (`FOR UPDATE SKIP LOCKED`, outcome recorded in the claiming transaction).

## Decisions

The owner supports D1–D5's direction (review of revision 1). D3's timing and D6 are revised as the owner asked.

- **D1, TRUNCATE: refused.** A row trigger doesn't fire on `TRUNCATE`, and a statement trigger can't name the tenants. A `BEFORE TRUNCATE` trigger on each table **raises**, for every role. Nothing truncates these tables today (checked: no code, test or tool). The event table is protected the same way.
- **D2, the in-code publishes: kept** as the fast path. `ProductService.invalidate()` already publishes directly after commit. The trigger outbox is the guarantee. A change then reaches subscribers twice, which is harmless (an extra eviction).
- **D3, the CI10 static guard: retired only after the complete replacement has passed CI and merged.** That happens in a later, separate PR. CI9 (the one path to full-tenant destruction) stays, because the trigger doesn't replace it. **Done (2026-10-23):** [spec 0022](0022-retire-ci10.md).
- **D4, how the relay wakes: polling.** It polls every 250 ms against a partial index, which works through PgBouncer's transaction pooling. `LISTEN`/`NOTIFY` would need a connection that bypasses PgBouncer, with polling still needed as the fallback.
- **D5, the resolver's negative entries: cleared on any tenants message.** The tenant resolver caches by host, and caches **unknown** hosts too (flood protection). A `{tenantId}` message can't name those entries. So on any `uv:tenants:invalidate` message, it evicts that tenant's entries **and every negative entry**. Only platform writes trigger these messages. Its stale-load guard is a **global** generation, which works before any tenant id is known (IO13).
- **D6, undelivered events (revised): expiry counts from after commit, against a shared, enforced maximum TTL.**
  - **The cap:** a shared constant `MAX_TENANT_CACHE_TTL_MS` (**60 s**, in `packages/contracts`) caps every instance's cache TTL; the default stays **30 s**. An instance configured above the cap **refuses to start**.
  - **The clock starts after commit:** each event gets a durable **first-observed** time, stamped by the database with `clock_timestamp()` when a relay first sees it. A relay can only see the event after commit, so this is never earlier than the commit.
  - **The database enforces the wait:** it refuses to mark an event `EXPIRED` until `first_observed_at + MAX_TENANT_CACHE_TTL_MS + 5 s` has passed.
  - **Why waiting that long is enough:** the products and resolver caches time their entries on a **monotonic** clock, from the start of the load (IO12). So by then every entry that could hold the pre-change value has expired, whatever the instances' wall clocks did.
  - **The clock assumption:** the database's own clock is the one assumption left. It must not step **forward** by a large amount between an event's first observation and its expiry. A forward step of that size would let expiry come early. Monotonic timers in the application can't protect against this; the database host's clock is disciplined by NTP and slewed, not stepped (IO12).

Only a publish that fails on its full 5 s budget, or reports Valkey unavailable, is a failure.<br>• **The transaction's limits, at three levels:**<br> ◦ the client gives the transaction a **3 s** timeout;<br> ◦ the relay role has PostgreSQL 18's `transaction_timeout = '5s'`, a server-side backstop on the whole transaction;<br> ◦ it also has `statement_timeout = '5s'` and `idle_in_transaction_session_timeout = '5s'`, which cover a single statement and an idle gap, not the whole.<br>• **The 2 s target,** from commit to eviction on every instance, is promised only under **healthy, no-backlog conditions**:<br> ◦ the relay is running and idle-polling every 250 ms;<br> ◦ **no other event is pending** when the change commits;<br> ◦ Valkey answers each publish within 100 ms;<br> ◦ every subscriber is connected.<br> The budget is at most 250 ms of polling, plus the claim, one publish and the subscriber's eviction.<br>• **Test, healthy:** 20 sequential changes, each with no backlog; every one is evicted on both API instances within 2 s of its commit (the maximum is recorded).<br>• **Test, backlog latency (separate, with no 2 s promise):**<br> ◦ 500 pending events across 100 tenants, on **both** channels, **interleaved** so that tenants repeat within a batch and across batch boundaries; each publish takes 100 ms;<br> ◦ delivery is FIFO by due time;<br> ◦ each pass's transaction ends within 3 s, and no event's attempts grow;<br> ◦ **the drain bound comes from two tested quantities.** A maximum publication rate (at most `floor(2 s ÷ 100 ms) = 20` per pass) gives only a _minimum_ number of passes, never a maximum: bookkeeping and deadline clipping can lower throughput below it. ## Design

**The shared maximum.** `MAX_TENANT_CACHE_TTL_MS = 60_000` lives in `packages/contracts`, so the API and the worker both import it.

- **Startup check:** the config schema gives `TENANT_CACHE_TTL_MS` (default 30 s) `.max(MAX_TENANT_CACHE_TTL_MS)`, so an instance configured above it fails validation and refuses to start.
- **Monotonic deadlines:** both caches record `performance.now()` at the start of a load and expire the entry at that time plus the TTL. `Date.now()` is no longer used for cache expiry.
- **In the database:** the migration defines the same value, as an immutable SQL function `public.cache_invalidation_max_ttl()`. A unit test reads the migration and checks the two are equal.

**The event table** (platform database, expand-only migration):

```sql
CREATE TABLE public.cache_invalidation_event (
  id                 uuid PRIMARY KEY DEFAULT uuidv7(),
  channel            text NOT NULL CHECK (channel IN ('uv:tenants:invalidate', 'uv:products:invalidate')),
  tenant_id          uuid NOT NULL,        -- no FK: the tenant may have just been deleted
  source             text NOT NULL,        -- e.g. 'tenant_product:UPDATE'; never row values
  created_at         timestamptz NOT NULL DEFAULT clock_timestamp(),  -- diagnostics only; never used for expiry
  first_observed_at  timestamptz,          -- stamped by the guard trigger: clock_timestamp() at first claim
  attempts           integer NOT NULL DEFAULT 0,
  next_attempt_at    timestamptz NOT NULL DEFAULT clock_timestamp(),  -- finite: fresh events never outrank due retries
  status             text NOT NULL DEFAULT 'PENDING' CHECK (status IN ('PENDING', 'PUBLISHED', 'EXPIRED')),
  settled_at         timestamptz,          -- stamped by the guard trigger on settlement
  last_error         text                  -- an error class only, as in spec 0002 B9
);
CREATE INDEX cache_invalidation_event_due ON public.cache_invalidation_event (next_attempt_at, id) WHERE status = 'PENDING';
CREATE INDEX cache_invalidation_event_settled ON public.cache_invalidation_event (settled_at) WHERE status <> 'PENDING';
```

**The capture function**, `public.capture_cache_invalidation()`, one for all three tables, with the channel as its trigger argument:

- **Triggers:** two per table. One is `AFTER INSERT OR UPDATE OR DELETE … FOR EACH ROW`, with no `WHEN` clause; the other is the TRUNCATE refusal. Both are `ENABLE ALWAYS`.
- **The `UPDATE` branch:**
  - It returns at once when `NEW IS NOT DISTINCT FROM OLD`, so a no-op update emits nothing. This check lives in the function because a combined trigger's `WHEN` can't reference `OLD` on `INSERT` or `NEW` on `DELETE`.
  - Otherwise it emits the old tenant id, plus the new one when it differs (IO4).
- **The other branches:** `INSERT` emits the new row's tenant id, and `DELETE` the old row's. The tenant id is `id` on `tenant`, and `tenant_id` on the other two tables.
- **Function settings:**
  - `SECURITY DEFINER`, owned by `univarse_migrator`;
  - `SET search_path = pg_catalog, pg_temp`, with `pg_temp` explicitly last;
  - every reference schema-qualified (`public.cache_invalidation_event`);
  - `REVOKE EXECUTE … FROM PUBLIC`. PostgreSQL checks `EXECUTE` when a trigger is created, not when it fires, so capture is unaffected.
- **Default function privileges:** `ALTER DEFAULT PRIVILEGES FOR ROLE univarse_migrator REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC`, so a future function doesn't silently gain `PUBLIC EXECUTE`.
- **No temporary tables:** the app and relay roles keep **no** `TEMPORARY` on the platform database. Each database is created `REVOKE ALL … FROM PUBLIC`, with only `CONNECT` granted.
- **What this is not:** business logic. The function records _that_ a row changed and which tenant it belongs to, nothing about what changed. ADR-031 amends docs/07's trigger rule to allow exactly this.

**The event table's own guards** (`ENABLE ALWAYS`):

- **Their security mode:** `SECURITY INVOKER`, with `SET search_path = pg_catalog, pg_temp`. They read only `OLD` and `NEW`, and call `public.cache_invalidation_max_ttl()` fully qualified, since the fixed search path excludes `public`.
- **Who runs them:** the relay role, which holds `EXECUTE` on that helper, or the migrator, as its owner and as the purge function's definer. The app role never reaches them, because it has no privilege on the table.
- **`PUBLIC EXECUTE`** is revoked on the guards and the helper, as on the other functions.

- **`BEFORE UPDATE`:**
  - It refuses any change to a settled row, and any change to `id`, `channel`, `tenant_id`, `source` or `created_at`.
  - It allows status only `PENDING` → `PUBLISHED`/`EXPIRED`, and stamps `settled_at := clock_timestamp()` on settlement.
  - It sets `first_observed_at := clock_timestamp()` the first time a claimed row is updated, ignoring any supplied value, and never changes it afterwards.
  - It refuses `EXPIRED` unless `first_observed_at IS NOT NULL AND clock_timestamp() >= first_observed_at + public.cache_invalidation_max_ttl() + interval '5 seconds'`.
- **`BEFORE DELETE`:** it refuses unless the row is settled and `settled_at < clock_timestamp() - interval '24 hours'`.
- **`BEFORE TRUNCATE`:** it raises.

**Roles and grants (IO17):**

- **The platform app role (`univarse_app_platform`):** `REVOKE ALL ON public.cache_invalidation_event`, which overrides the default privileges that would otherwise give it full DML.
- **The relay role (`univarse_relay_platform`), new:**
  - `LOGIN`, `NOSUPERUSER NOCREATEROLE NOBYPASSRLS`, `CONNECT` only, no `TEMPORARY`;
  - `GRANT USAGE ON SCHEMA public`, needed because the schema's `PUBLIC` privileges are revoked;
  - `GRANT SELECT, UPDATE (attempts, next_attempt_at, status, last_error)` on the event table;
  - `GRANT EXECUTE` on `public.cache_invalidation_max_ttl()` and `public.purge_settled_invalidation_events(integer)`;
  - role settings: `transaction_timeout = '5s'` (PostgreSQL 18), `statement_timeout = '5s'` and `idle_in_transaction_session_timeout = '5s'`;
  - behind PgBouncer, it is its own pool, and role settings apply to each server session.
- **The relay's credentials reach only the worker:**
  - `setup-local` writes `PLATFORM_RELAY_URL` to a separate, git-ignored **`.env.worker`**, never to the repo-root `.env`. Today the API's development preload (`otel.ts`, then `main.ts`) loads the whole root `.env`.
  - `worker.ts`, and `otel.ts` when it starts the worker, also load `.env.worker`. The API path never does.
  - The API's config refuses to start if `PLATFORM_RELAY_URL` is set (IO17).
  - In CI, the role step exports the URL only to the worker's steps and to the worker container in the journeys.
  - Relay integration tests load `.env.worker` explicitly.
- **The purge function:** `SECURITY DEFINER` with the same safeguards. It deletes at most `limit` rows, each settled for more than 24 h. The `BEFORE DELETE` guard enforces the same rule underneath it.

**The relay, `PlatformInvalidationRelay`,** runs in the worker, on the relay role's connection:

1. **Claim:** in one transaction with a **3 s** client timeout (and the role's 5 s `transaction_timeout` behind it), select up to 200 `PENDING` events with `next_attempt_at <= statement_timestamp()`, `ORDER BY next_attempt_at, id`, `FOR UPDATE SKIP LOCKED`. Then touch them once, so the guard stamps any missing `first_observed_at` (IO7, IO10, IO12).
2. **Expire (D6):** mark `EXPIRED` the claimed events whose `first_observed_at + max + 5 s` has passed. The guard trigger checks the bound, so a wrong relay can't expire early. They are counted in a warning.
3. **Coalesce:** publish each distinct `(channel, tenant_id)` once, oldest first (IO18).
4. **Publish** through `InvalidationBus.publish`, until the **2 s batch deadline**, with each publish's timeout set to `min(5 s, time left)` (IO11).
   - On success, that pair's events become `PUBLISHED`.
   - **Deadline exhaustion:** at the deadline, or when a publish times out on a budget the deadline clipped, stop. The remaining events stay `PENDING`, unchanged.
   - **Failure:** when a publish fails on its full budget, or reports Valkey unavailable, stop. The remaining events get `attempts + 1`, a backoff and their error class.
5. **Commit.** A crash before this point leaves every claimed event `PENDING`: before a publish, IO8; after one, IO9.
6. **Housekeeping:** at most once a minute, call the purge function (IO18).

The loop polls every 250 ms when idle (D4) and immediately after a pass that stopped at its deadline or claimed a full batch. Passes never overlap.

**Consumers:**

- **Products:** unchanged. `ProductService` already subscribes in the API and the worker, with its generation guard. Its entry lifetime already counts from the start of the load; IO12 makes that a tested requirement.
- **The tenant resolver** (API) gains a subscriber on `uv:tenants:invalidate`, which today has none:
  - It evicts the tenant's entries and every negative entry (D5).
  - It gains the **global** generation guard (IO13).
  - Its whole-cache `invalidate()` stays, and bumps the generation.

**Ordering and timing:**

- **Three clocks, each for one job:**
  - `clock_timestamp()` stamps due times, first observation and settlement: the actual time of the write;
  - `statement_timestamp()` is the claim's cutoff: the time the claim command was **received**. An event committed before the claim is sent is due by then. One committed in the brief window between receipt and the statement's snapshot may be visible but not yet due; it is claimed in the next pass, 250 ms later. Correctness doesn't depend on that window: only latency does;
  - `now()`, the transaction's start, is used for neither, because a relay transaction can begin before a commit it later sees.
- **Publish follows commit by construction:** the relay can only see an event once its change has committed. An eviction can therefore never arrive before the change it announces.
- **The order between events doesn't matter,** because every message means the same thing: evict this tenant.
- **The 2 s target holds only under IO11's healthy, no-backlog conditions.** Backlog latency is measured separately. The shared maximum TTL bounds staleness in every case, under IO12's clock contract.

**What stays open, stated plainly:**

- **The owner role can still bypass capture.** `univarse_migrator`, or a superuser, can disable or drop the triggers and functions. Nothing at the database level stops the owner role. The IO15 gate detects it the next time it runs; it does not prevent it.
- **A subscriber that is down when a message is sent** still relies on the cache TTL, now capped by the shared maximum. Pub/sub doesn't queue for absent subscribers.
- **The database clock** must not step forward by a large amount (D6, IO12). Application timers are monotonic, so instance clock steps no longer matter. A large forward step on the database host could let an event expire early, so that host's clock is NTP-disciplined and slewed. This is stated, not enforced.
- **The keyring's forget** (`uv:keys:forget`) stays on its in-code path. Key destruction already publishes after commit with an honest report (spec 0015 CI5–CI9), and `tenant_data_key` is not in scope here.

## Owner review of revision 4

The owner found the claim test and the ADR corrections right. One IO11 correction and one wording fix were requested.

1. **The drain bound needs a tested minimum throughput (IO11):**
   - **The problem:** "at most 20 publications per pass" gives a minimum number of passes, not a maximum. Bookkeeping and deadline clipping can lower throughput (40 publications at 19 per pass need three passes, where `ceil(40 ÷ 20)` gives two), and a fixed allowance doesn't establish a minimum throughput either.
   - **Now:** the bound is `ceil(500 ÷ m) × T`, with `m` (the minimum number of events settled per non-final pass, 10) and `T` (the maximum pass duration plus the delay before the next, 3.25 s) each asserted per pass.
   - **Kept as evidence:** the publication counts and the grouping tests. `P` is defined as successful publications whose settlement committed, in the crash-free workload. Possible duplicates from clipped timeouts or uncommitted passes are counted separately.
2. **`statement_timestamp()` wording:** it records the time the command was received. The spec no longer claims it follows every commit the statement can see. The paused test commits before sending the claim, which is why the cutoff is correct there. A commit inside the receipt-to-snapshot window only delays its claim by one pass.

## Implementation notes (PR A)

**Scope.** The owner approved the split on 2026-10-18. PR A: the migration (table, triggers, functions, guards, grants), the relay role and its credentials, the TTL cap, the IO15 gate, the relay, and IO1, IO2, IO4–IO11, IO14–IO18 (IO12's database parts: the stamp, early expiry refused, the cap). PR B: the monotonic caches, the resolver's subscriber and global generation (IO13), and IO3 and the rest of IO12, end to end across instances.

**Decisions made while implementing, for the owner's approval:**

1. **The relay goes through PgBouncer in the isolation job.** `db:setup` adds the relay role to the auth file and writes `PGBOUNCER_PLATFORM_RELAY_URL` to `.env.worker`; it is its own pool. The PB3 suites set `UNIVARSE_RELAY_THROUGH_PGBOUNCER=1`, so the same tests run direct and pooled.
2. **The event table is a Prisma model; the triggers, functions and grants are hand-written SQL** in the migration. The relay uses raw SQL on its own platform client.
3. **Test seams are constructor options:** a pause after `BEGIN`, after the claim and before the commit; the clock; the jitter; the publish function. The crash tests terminate the relay's backend **as the relay role** (a role may signal its own backends; no superuser). IO8's crash also aborts the pass: killing the connection alone doesn't stop the JavaScript from publishing before its next statement fails.
4. **Only `worker.ts` loads `.env.worker`.** The Design also names `otel.ts` "when it starts the worker", but `otel.ts` never reads the relay's URL, so loading it there would only widen where it lives.
5. **The worker refuses to start without `PLATFORM_RELAY_URL`** (an error naming `pnpm db:setup`). The `keys` CLI, which reuses the worker module, never gets a relay: its config is the API kind, which refuses the URL.
6. **The relay's tests read `.env.worker` only, never `process.env`,** so a test process never holds the URL where the API's config would see it. `tools/images/container.mjs` passes it to **worker** containers only, by name (`-e`), read from `.env.worker`; API containers never receive it.
7. **The IO15 gate also checks that `cache_invalidation_max_ttl()` equals `MAX_TENANT_CACHE_TTL_MS`.** Two tests shorten it briefly and restore it in `finally`; a run that dies in between is caught by the next `pnpm rls:check`.
8. **`last_error` is a fixed label**, `PublishTimeout` or `PublishFailed`, never the client's message. The backoff's ±20 % jitter never exceeds the 5 s cap. A pass that throws (the database unreachable) makes the loop wait 250 ms doubling, at most 5 s.
9. **`.env.worker` is written like the root `.env`** (mode 0600 when created), not with spec 0017's `writeOwnerOnly`, which restricts the parent directory to the owner: here that is the repository root. The root `.env` already holds the more powerful migrator password.
10. **ESLint's default-project cap rises from 16 to 24** for the two new files under `packages/db/scripts` and `packages/db/test`.
11. **Owner action after merging:** rerun `pnpm db:setup` before `pnpm db:migrate` (it creates the relay role, writes `.env.worker`, and rotates local passwords). The local release flow's worker container needs `.env.worker` too.

## Implementation notes (PR B)

**Scope:** IO3, IO13, and the rest of IO12 (monotonic deadlines from the load's start; the long transaction; differing instance TTLs).

**Decisions, for the owner's approval:**

1. **The resolver subscribes** to `uv:tenants:invalidate` when its module starts, as `ProductService` does. A message evicts that tenant's entries and every negative entry (D5).
2. **One global generation,** bumped by every tenants message and by `invalidate()`; a lookup caches its result, positive or negative, only if it is unchanged since the lookup began (IO13).
3. **Both caches use `performance.now()`** from the start of the load. The unit tests step `Date.now()` back and simulate slow loads, with no new seam.
4. **IO13's held lookup** is tested on a resolver built with a client whose read is held open, and its own subscribed bus, with the real relay and database. IO3 and the new-host test use two real API instances. The IO12 timing tests shorten the database's maximum to 3–4 s and restore it in `finally`.
5. **"The relay's own configured TTL"** (IO12): the relay has none. It never reads `TENANT_CACHE_TTL_MS` and expires only against the database's bound, which the guard enforces.

**Evidence (local, isolated stack).**

- Unit: API 298/298, including the resolver's and the products cache's 7 new tests.
- `shared/tenancy/tenant-invalidation.int.spec.ts` 5/5: every writer of IO3 reaches both instances within 2 s; a new and a newly verified host resolve on both within 2 s; the overtaken negative lookup isn't cached; expiry waits for first observation + max + 5 s in both IO12 tests.
- **IO19 mutations, each failing its intended test:** `Date.now()` deadlines and lifetime from the load's end, for each cache (the unit tests); no negative-entry eviction (unit and the new-host test); no resolver generation (unit); a per-tenant generation (unit and the in-flight test); no resolver subscriber (IO3); expiry counted from the change rather than its first observation (the long-transaction test).
