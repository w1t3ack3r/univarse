# Spec 0015: Cache isolation — product entitlements and key "forget" on the invalidation bus (cross-tenant suite, layer 5)

**Status:** **Implemented (2026-10-13)**; met once reviewed and green in CI. **Accepted (2026-10-13)** by the owner, after review of revisions 1 and 2 (#65). D1 (no acknowledgements) and D2 (keep the 1-hour TTL) are decided. Acceptance added two CI7 edge-case tests (an unwrap finishing after the full TTL; old callbacks meeting a replacement load) and corrected the TTL reference to E5.
**Phase:** 0. It closes the "Cache isolation" item of [docs/18](../18-roadmap.md): product-cache invalidation (spec 0003 P7) and key-forget propagation (spec 0006). That completes layer 5 of [docs/12 §3](../12-testing-strategy.md) for today's caches.
**Builds on:**

- [spec 0007](0007-settings.md) ST10/ST11: the settings cache and its Valkey invalidation bus, the pattern reused here;
- [spec 0003](0003-product-entitlements.md) P7: the products cache;
- [spec 0006](0006-envelope-encryption.md): the keyring cache (E5/E6) and the destruction boundary;
- [02 §7.3](../02-architecture.md): tenant cache TTLs.

## Why

Three per-instance caches hold tenant-scoped, security-relevant state. Today only the instance that made a change evicts anything, and only for one of them.

| Cache                             | Holds                        | Today                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | Risk                                                                                                                                                   |
| --------------------------------- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ProductService` (API and worker) | the tenant's active products | The changing instance evicts locally; others converge within the TTL (30 s). **No generation guard:** a read that began before the eviction can re-cache the old set. Its expiry is computed from the read's **start**, so a stale re-cache lasts at most one TTL from that start.                                                                                                                                                                                           | A disabled product stays usable on other instances for up to 30 s, and briefly on the changing instance itself through the re-cache race.              |
| `TenantKeyring` (API and worker)  | **unwrapped DEKs**           | `forget(tenantId)` exists, but **nothing calls it**. Key destruction runs in the `keys` CLI, a separate process. Three more defects, from the owner's reproduction:<br>• **The load race:** a pending unwrap that finishes after `forget()` re-caches the key, and `key()` returns it again.<br>• **Expiry only on lookup:** an idle expired key stays cached and un-zeroed.<br>• **The deadline restarts:** expiry is computed after the unwrap, so a slow load extends it. | After crypto-shredding, running processes keep decrypting with the destroyed key for up to **1 h** (the E5 TTL), and possibly longer through the race. |
| `TenantResolver` (API)            | host → tenant, and status    | No writer exists in the app; tenants change only via seed or DB.                                                                                                                                                                                                                                                                                                                                                                                                             | None today. A future writer (the console) must not ship without invalidation.                                                                          |

OWASP's multi-tenant guidance treats cache invalidation as part of tenant isolation (spec 0007 §Why). This spec puts the products and keys caches on the bus, closes the keyring's own races, and binds the future writers.

## Decisions (owner, 2026-10-13)

- **D1: no acknowledgements.** Pub/sub has no delivery receipt. The CLI reports what it knows (CI6), never that subscribers forgot.
- **D2: keep the keyring's 1-hour TTL** as the lost-message bound, consistent with spec 0006's destruction boundary. It will be revisited with the shred ledger.

## Design

- **One small bus helper, `InvalidationBus`:**
  - publishes after commit, with a bounded attempt (CI6), and never throws;
  - one dedicated subscriber connection per process, which never blocks startup;
  - zod parsing per channel.
  - Products and keys use it. **Settings stay as built in spec 0007,** and can move onto the helper later with no behaviour change.
- **Products:** the cache gains a per-tenant generation; `setEnabled` publishes in its `finally`, so the compensated path is covered; the outbox worker subscribes too, because it checks products (B10).
- **Keys:**
  - **The CLI** connects to Valkey only to publish. It never subscribes, and never needs the API.
  - **Forgetting a tenant drops every version, cached and in flight.** The next decrypt unwraps the live versions again (one Vault call each); destroyed versions fail.
  - **The keyring's guard** follows CI7: a generation recorded at load start and checked before caching; the deadline set at load start; a timer per entry that zeroes on expiry; zeroing on every discard.
  - **Cipher operations own a private copy of the key** (`withKey`), so eviction, which zeroes the cached buffer, can never reach a key in use.
  - **The reported fallback deadline** is destruction time plus the shared one-hour ceiling on any keyring TTL, never the sender's own TTL.
- **Valkey trust:** as in spec 0007, Valkey is trusted infrastructure on the private network. A forged message can only cause an extra eviction (a cache miss), never a wrong value, which is why messages carry no values.

## Owner review of `c6dd715` (#66): three gaps and three smaller points, fixed

**1. Eviction could corrupt encryption: scoped key ownership.**

- **The gap:** with the cache full, a concurrent load could zero the cached DEK between `FieldCrypto` obtaining it and using it, so the ciphertext was sealed under an all-zero key. The owner reproduced it.
- **The fix:** `TenantKeyring.withKey(tenant, version, fn)` gives `fn` a **private copy**, taken synchronously from a live cache entry in the same tick it is read, and zeroes the copy when `fn` settles. After a load it re-reads the cache rather than trusting the returned buffer. An all-zero copy fails closed.
- **Callers:** `FieldCrypto.encrypt`, `decrypt` and `reencrypt` all use it. `key()` remains for inspection only, documented as unsafe for cipher work.
- **Cache zeroing is preserved:** eviction still zeroes the cached buffer at once.
- **Regression tests (`keyring.spec.ts`):**
  - an eviction mid-operation, by `forget` and by a full cache (`maxEntries: 1`), never changes the key in use, and the copy is zeroed after;
  - `FieldCrypto` with an eviction exactly in the obtain-to-use window, starting cached and uncached: the ciphertext opens with the tenant's real key and **never** with an all-zero key;
  - `FieldCrypto` never calls `key()`.
- **Mutations:** with `encrypt` back on the cached buffer, the behavioural test fails, so it reproduces the owner's probe. With `withKey` handing out the cached buffer instead of a copy, the eviction test fails.

**2. The fallback deadline used the sender's TTL: now the shared ceiling.** The report says destruction time + `KEYRING_MAX_TTL_MS` (one hour, the cap every keyring enforces), because no deployment-wide shorter bound is established. A CI6 test runs a 1 s-TTL CLI against an API instance on the 1-hour default with a lost notice. The report says + 1 h, and the receiver **still holds the key after the sender's 1 s**, so a sender-TTL deadline would have been false.

**3. CI10 didn't enforce publication: now it fails closed.**

- **What counts as a write:** **any** write to `tenant`, `tenant_host` or `tenant_product` in production code, in any form the guard recognises:
  - a delegate call, with or without a leading dot, including `upsert` and the `…AndReturn` variants;
  - raw `INSERT`/`UPDATE`/`DELETE` SQL;
  - dynamic `['tenant']` delegate access.
    Variable-based `data` doesn't matter, because every write call counts.
- **Reviewed writers only:** such a write is refused unless its file is a **reviewed writer**. A reviewed writer must make an actual `.publish(<channel>, …)` call, with comments stripped and a bare mention of the channel not counting, and must name a post-commit publication test that exists. A reviewed entry whose file no longer writes fails as stale.
- **Today's one reviewed writer:** `product.service.ts` (`tenant_product.enabled`). Its proof is a new test: with an audit failure injected, the toggle is compensated and a publish still follows.
- **Self-tests** cover every recognised form, a comment-only channel, a mention-only channel, a real publish, a stale entry, and reads.
- **Mutations:** no comment stripping; no raw-SQL pattern; no dynamic-access pattern; a loose publish check. Each is caught.

**Smaller points:**

- **CI3:** the 150 ms sleep is replaced by a "the old DB result was captured" signal from inside the held read, and the delivery wait is asserted.
- **CI8:** the wait for both messages is asserted to have succeeded before B's cache is checked.
- **`publish()`:** message validation now sits inside its error boundary. A new unit test (`invalidation-bus.spec.ts`) shows an invalid tenant id is reported as unconfirmed and never thrown, with nothing sent; a hanging publisher is cut off at the timeout; a rejecting one is reported. Moving validation back outside the boundary fails the test.

**Runs after the fixes:**

- **Two back-to-back combined runs** of the six affected integration files (cache isolation, products, outbox, settings, key rotation, key-sweep isolation): **79/79 each**.
- **Units:** API 168/168, crypto 26/26. Lint and typecheck are clean.

**Two test-harness faults found by the combined runs, fixed:**

1. **CI1 lost a message.** A message published right after a fresh instance started could race that instance's `SUBSCRIBE`, and then CI1's failure left `helpdesk` enabled, cascading into later tests. `InvalidationBus.ready()` now resolves once every requested subscription is acknowledged. The tests await it before publishing; production startup never waits on it.
2. **CI4 timed out** after that change: the helper awaited `ready()` on an instance whose Valkey is deliberately unreachable, whose `SUBSCRIBE` can never be acknowledged. The helper skips it for such instances. The Valkey-down behaviour is unchanged: startup doesn't wait, reads go to the DB, writes commit, and publishing is bounded and never throws (CI4, CI6).

**Recorded as unexplained:**

- **The failure:** in the first combined run, the key-sweep isolation tests JI5–JI7 failed. That run's output was captured only through a `grep`, with no error text. They passed alone, and in the three combined runs since.
- **The cause is not established.** Separate test processes rule out shared in-memory state, but **not** interference through the shared Postgres or Valkey.

## Owner review of `6d42a3a` (#66): the remaining CI10 gaps, closed

**The owner's typed fixtures produced zero violations for:**

- nested relation writes through a `data` variable, or with quoted `'tenant'` / `'update'` keys;
- ``$executeRawUnsafe(`${sql}`)``, and a raw method extracted with `.bind()`;
- a local `CHANNELS` whose `tenants` value is the products channel;
- a restricted helper invoked through `.bind()`;
- a same-named method on another class standing in for the publisher.

- **Mutation inputs:** writes on any delegate whose model can reach a guarded model must have literal `data`, `create` and `update`, looking through type-only casts. Quoted keys are normalised; spreads, computed keys, shorthand or variable `data`, and non-literal relation values are refused.

### A recommendation for the owner: move this guarantee into the database

The static guard now covers every bypass found so far, but it is an analysis of TypeScript, and the guarantee CI10 wants ("every change to these tables reaches every instance's caches, after it commits") is about **writes**.

- **What a static guard can't see:** another service, a migration, a seed, an operator's `psql`, or a future language feature can still write without publishing.
- **The alternative:** a database trigger on `tenant`, `tenant_domain` and `tenant_product` that records each change in an invalidation outbox table, in the **same transaction**. The existing outbox relay then publishes to Valkey only after commit.
- **What that buys:**
  - **Any writer is covered**, whatever its form or language.
  - **Order holds by construction:** a rolled-back write leaves no outbox row.
  - **No allow-list to maintain.**
- **The cost:** a migration (expand-only), relay latency (still within the 2 s target if the relay polls that often), and a trigger test per table.
- **Suggested scope:** a follow-up spec, with the static guard kept as a fast early warning, or retired if the trigger is accepted as the enforcement.

**Not decided here: this is the owner's call.**

## Owner review of `436195e` (#66): parameters, tags, lexing and relation links

**The owner's probes (TypeScript 5.9.3) found four gaps that returned no violations:**

1. **Fragment unions and generics:** `Sql | string` and `T extends Sql` passed the exact-name check.
2. **Untrusted tags:** ``$executeRaw(makeQuery`SELECT 1`)`` passed, even when `makeQuery` returns SQL that updates `tenant`.
3. **Comment markers inside strings:** in `WITH c AS (SELECT '-- literal') UPDATE tenant …`, normalisation erased the real `UPDATE`.
4. **Relation links:** `Tenant.products.connect(…)` passed with only a tenants-channel binding, though it moves the product to another tenant.

**The fixes** (`apps/api/src/testing/cache-writer-guard.ts`):

- **Parameters, by proof:** an interpolation is accepted only when its type proves it is sent as a bound parameter. That means a primitive (literal types and enums included), `Date`, or an array or tuple of them. Every union member must qualify, a type parameter is judged by its constraint (unconstrained means `unknown`, refused), and an intersection only as a branded primitive (`string & { readonly __brand: … }`).
- **Tags, by declaration:** a template passed to a raw method is accepted only when its tag resolves to the `sql` declared in the generated `prismaNamespace.ts` (`Prisma.sql`). A function named `sql`, or any other tag, is refused.
- **A quote-aware lexer:** `lexSql` follows PostgreSQL's rules for standard, `E'…'` and dollar-quoted strings, quoted identifiers, nested block comments and line comments. Unterminated input, or a backslash in a standard string (whose meaning depends on `standard_conforming_strings`), is refused. Literal contents are scanned as SQL as well, so the lexer can't hide `DO $$ UPDATE tenant … $$` or `EXECUTE 'UPDATE tenant …'` by treating them as strings.
- **Relation operations, all classified:** `create`, `createMany`, `connectOrCreate`, `update`, `updateMany`, `upsert`, `delete` and `deleteMany` write the related row. `connect`, `disconnect` and `set` write it when the foreign key is on the related side; this is read from the Prisma schema (`@relation(fields: …)`). Any other operation is refused.

**Regression fixtures** (the guard spec now has 10 tests):

- `Sql | string` and `T extends Sql` interpolations: refused.

- `'-- literal'`, `E'it\'s -- x'` and `$q$ /* $q$` before a real `UPDATE`, and `/* it's */` before one: each `UPDATE` recorded.
- `DO $$ BEGIN UPDATE /* x */ tenant … END $$`: recorded. An unterminated literal: refused.
- `Tenant.products.connect` with a tenant-only binding: the `tenant_product` write is refused for lack of a binding. An unknown operation (`link`): refused. The control, `TenantProduct.tenant.connect` (the foreign key is on the product): only the product row is written.

**Mutation checks:** eleven, each caught by its intended assertion. They cover:

- any tag, or a tag matched by name;

## Owner review of `f0b6ab1` (#66): the SQL path, tokenised and decoded

**The owner's probes (TypeScript 5.9.3) found three gaps in the SQL path:**

1. **Carriage returns:** a `--` comment ended only at `\n`, but PostgreSQL also ends it at `\r`. So `UPDATE -- note\r tenant …` reduced to `update`.
2. **Decoding and continuation:** literal SQL was scanned before PostgreSQL's decoding and continuation rules applied. These passed:
   - `EXECUTE E'UPDATE \x74enant …'` inside `DO`;
   - a `U&'…' UESCAPE` spelling of `tenant`;
   - `'UP'` and `'DATE tenant …'` on consecutive lines, which PostgreSQL joins.
3. **Target matching:** each of these passed:
   - `UPDATE public . tenant`;
   - `UPDATE"tenant"`, where the quoted identifier lost its token boundary;
   - `UPDATE ONLY(tenant)`;
   - `TRUNCATE tenant_domain, tenant_product` with only a `tenant_domain` binding: the second table went unchecked.

**The fix, a token-based SQL path** (`lexSql` and `sqlWrites` in `apps/api/src/testing/cache-writer-guard.ts`):

- **Tokens, as PostgreSQL's scanner makes them:** whitespace and comments separate tokens. A line comment ends at LF or CR, block comments nest, and a quoted identifier is its own token.
- **Literals decoded, or refused:**
  - Every `E'…'` escape is decoded, and adjacent string constants are joined. Each piece is also read on its own.
  - `U&'…'` and `U&"…"` are refused, because a `UESCAPE` makes their decoding depend on context.
  - A backslash in a standard string is refused, as is anything unterminated.
  - A string constant is read as SQL itself (recursively, up to four levels deep), and a refused form inside one is refused outright.
- **Targets, failing closed:** the regex is gone. In any statement with a data- or schema-changing keyword (`insert`, `update`, `delete`, `merge`, `truncate`, `alter`, `copy`, `drop`, `create`), every word or quoted identifier naming a guarded table is a write to it. The one exception is `update` after `for` or `key`, which is a row lock.
  - This covers qualification, parentheses and lists.
  - It also over-approximates: a guarded table that a write statement only reads (`INSERT INTO x SELECT … FROM tenant`) counts as a write and needs a binding. No production SQL is affected.

**Regression fixtures** (the guard spec now has 11 tests):

- Your probes, exactly:
  - the CR-ended comment, with LF and CRLF controls;
  - the `\x74` `DO`/`EXECUTE`, the `U&'…' UESCAPE '!'` spelling (refused), and the two-line `'UP'` / `'DATE tenant …'`;
  - `public . tenant`, `UPDATE"tenant"` and `ONLY(tenant)`;
  - `TRUNCATE tenant_domain, tenant_product` with a `tenant_domain`-only binding.
- **Controls:**
  - a decoded `E'SELECT \x74enant_id …'` inside `DO` is a read;
  - without bindings, the `TRUNCATE` reports both tables;
  - `SELECT … FROM tenant … FOR UPDATE; UPDATE file_object SET tenant_id = …` gives no violations.

**Mutation checks:** ten, each applied alone and run against the new test.

- The unchanged guard of `f0b6ab1` fails it, at the CR case.
- Each of the following fails it at its intended assertion:
  - line comments ending only at LF;
  - no `\xhh` decoding;
  - `U&` not refused;
  - constants not joined;
  - quoted identifiers not matched;
  - only the first target counted;
  - only the token after the verb counted;
  - a row lock counted as a write (fails the control);
  - string constants not read as SQL.

The list is in `test-results/spec-0015-review-f0b6ab1/mutations.txt`.
